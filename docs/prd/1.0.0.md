# Lager 1.0.0 product specification

Implementation status: Partial

This document defines Lager 1.0 behavior and acceptance criteria. Section status tracks implementation, not requirement approval: **Not started**, **Partial**, **Implemented**, **Verified** against acceptance criteria, or **Not applicable** for descriptive sections.

## 1. Product goal

Implementation status: Not applicable

Lager manages a declarative collection of local Git repositories. It provides explicit commands, a persistent repository inventory, and independent worktree utilities.

- **Repository management:** declare, clone, inspect, reconcile and safely remove repositories.
- **Inventory:** browse repository roots and declarations, inspect their state, and act on one or multiple repositories without leaving the interface.
- **Worktrees:** create, list and remove local working copies through native Git.
- **Independent operations:** registration, checkout availability and worktree management are separate concerns; no prescribed start/resume/finish lifecycle.

Forklift and terminal-host integration belong to [2.0](2.0.0.md), not this release.

## 2. Terms and ownership

Implementation status: Not applicable

| Term | Meaning |
| --- | --- |
| Repository identity | Normalized host and repository path used to compare references. |
| Declaration | Portable configuration identifying a repository or wildcard set to keep available. |
| Checkout | A concrete local working directory; one identity can have multiple checkout paths. |
| Primary checkout | A repository's main working directory, distinct from its linked worktrees. |
| Worktree | An additional working directory managed through native Git worktree operations. |
| Inventory entry | A declaration, discovered primary/standalone checkout, or remote candidate. |

Lager owns declarations, application operations and interface state. Git owns repository metadata and worktree bookkeeping. Registration does not imply files exist; removing a worktree does not delete its branch.

### 3.1 Commands

Implementation status: Implemented

| Command | Required behavior |
| --- | --- |
| `init` | Create configuration once; select the root and optionally create it and configure GitHub. Interactive defaults are `repos`, create root, and configure GitHub. Missing optional tools produce diagnostics without blocking initialization. |
| `register [REPOSITORY]...` | Declare concrete repositories or trailing wildcards; support explicit post-clone hooks and archive filtering during discovery. |
| `unregister [REPOSITORY]...` | Remove equivalent explicit declarations and exclude concrete members from every matching wildcard. Preserve files. |
| `add [REPOSITORY]...` | Clone with an explicit or interactive registration choice. Matching destinations are no-ops. `--post-clone` implies registration. Preserve successful clones after partial failure. |
| `remove [REPOSITORY]...` | Delete guarded standalone checkouts. Support unregister/keep-registered choices, confirmation and bounded force. Change registration only after successful deletion or verified absence. |
| `ensure` | Sequentially create missing effective declarations; never pull/reset existing checkouts. Continue independent failures and report aggregate failure. |
| `hook [REPOSITORY]...` | Rerun declared hooks explicitly; report repositories with no hook. |
| `list`, `ls` | Identical non-interactive declaration reports, arguments, output and exits. Offline by default; `--remote` expands wildcards. Human output is tab-separated; `--json` uses the versioned list schema. |

CLI registration validates its batch before committing the config mutation; inventory uses the per-target boundaries in §4.5. Explicit arguments bypass pickers; omitted-argument repository selectors use `fzf` and support multi-selection. Full options and prompt defaults are defined in the [CLI reference](../reference/cli.md).

### 3.2 References and configuration

Implementation status: Partial

Repository references, provider discovery and config persistence are implemented.
Worktree-default configuration remains Not started under §5.1.

- Accept canonical identities, GitHub shorthand, SCP/SSH/HTTP(S) and file clone URLs. Normalize comparison while retaining configured clone URL text.
- Discover through configured GitHub (`gh`), Bitbucket Cloud and Bitbucket Data Center providers, including pagination, archive filtering and partial-success reporting. Validate selected clone links after archive filtering; unused links and excluded archived repositories do not invalidate discovery.
- Apply provider prefixes and relative destination layouts, trailing wildcards, exclusions and explicit-declaration precedence.
- Registering a concrete wildcard member removes its exclusions from **every matching pattern**. Create an explicit declaration when no pattern covers it or an explicit hook requires one. Unregister removes equivalent explicit declarations and excludes the member from **every matching pattern**.
- Select configuration by `--config`, then `LAGER_CONFIG`, then the HOME-derived default. Persist portable TOML, never expanded machine-specific paths or secrets.
- Validate before operations; warn about unknown keys while preserving them. Reject forbidden credentials and URL queries/fragments before persistence or execution, including spellings normalized by URL parsing. Keep rejected values out of diagnostics. TOML syntax/type errors report line and column when available without printing source values.
- Use symlink-aware target resolution, mutation locking, atomic writes and permission preservation. `init` refuses an existing config path, including a dangling symlink.

Provider credentials are environment references. Worktree defaults use the same configuration store. See the [configuration reference](../reference/config.md).

### 3.3 Process and removal contracts

Implementation status: Partial

Removal guards, native streams, output escaping and observed child SIGINT/status
130 handling are implemented. External interruption can terminate Lager before
child-result handling or cleanup; universal signal-driven restoration remains
incomplete under §6.1.

Native Git handles authentication and transport; Git and hook streams remain visible. Non-interactive commands never prompt and require explicit choices. Exit codes are success/no-op/skip `0`, operational/aggregate failure `1`, usage error `2`, and cancellation `130`.

`list --json` emits only its [versioned document](../reference/list-json.md) on stdout; diagnostics use stderr. Its states are `missing`, `cloned`, `conflict` and `unreadable`; offline wildcards remain patterns. Inventory's local discovery and originless distinctions do not alter this contract.

Lager-owned human fields escape C0/C1/DEL controls and literal backslashes before
adding renderer-owned separators. JSON retains original serialized values and
native Git/hook streams remain untouched. Picker labels map to original
candidates rather than being parsed into execution values.

Repository deletion requires an exact standalone, non-bare checkout inside the configured root with a matching supported origin. Reject the root itself, symlinks, unreadable/plain directories, linked worktrees and mismatched identity. Block primary-checkout deletion while dependent linked-worktree metadata exists, including stale or locked entries.

Repository `--force` may accept disclosed local-state warnings: tracked/untracked/ignored files, stashes, submodule changes, detached or unsafe branch state, missing upstream and unpushed work. It cannot waive path, ownership, origin or dependency guards. Confirmations default to no; non-interactive removal requires `--yes` and a registration choice. A selected path that vanishes fails rather than authorizing deletion or unregistering another location.

## 4. Inventory

Implementation status: Not started

### 4.1 Sources and identity

Implementation status: Not started

`lager inventory` and `lager inv` open the same persistent table. Default sources are declarations and repository roots beneath configured `root`, without provider requests.

- Traverse without a depth limit, stopping at each Git root. Do not follow directory symlinks or descend into discovered repositories.
- Exclude linked worktrees, submodules, nested repositories inside a found root, non-Git directories and bare repositories. Diagnose unreadable paths and unsupported bare repositories; do not claim a partial scan is complete.
- Include missing declarations, unregistered checkouts and originless repositories. Label originless entries “No origin” and identify them by exact path; never guess another remote or declaration relationship.
- Keep duplicate-origin checkouts path-distinct. Merge a checkout with a declaration only when both normalized identity and configured destination match.
- Warn about nonstandard checkout locations with both found and configured paths. Registration does not adopt or move a checkout; a checkout elsewhere does not satisfy a missing configured destination.
- Show local wildcard matches individually and the wildcard declaration separately, respecting exclusions and explicit precedence. Unknown remote membership never implies invented missing entries or complete reconciliation.

Registration and checkout state are independent attributes. Conflict, unreadable and unknown states must not appear as missing or safely cloneable.

### 4.2 Table and navigation

Implementation status: Not started

Build the TUI with Ratatui and Crossterm. Columns are **repository, path, registration, checkout, origin, branch, changes**. Load Git status in the background; pending/error is never displayed as clean. A detail area exposes full values, warnings and unavailable-action reasons.

Normal mode uses `j`/`k` for rows and `h`/`l` for columns; arrows are equivalent. `/` enters live fuzzy search across attributes, full paths and origins. Search-mode action letters are text. Enter or Esc returns to normal mode retaining the filter; normal-mode Backspace clears it.

| Normal-mode key | Action |
| --- | --- |
| `r`, `u` | Register, unregister |
| `c`, `C` | Clone only, clone and register |
| `d`, `D` | Remove only, remove and unregister |
| Space, `a`, `A` | Toggle current mark, mark visible concrete rows, clear all marks |
| `R` | Refresh local/config state |
| `m` | Action menu: Add, remote controls, batch cancellation |
| Enter, `y`, `o` | Inspect current cell, copy full value, open origin web URL |
| `?`, `q` | Help, quit |

Row mutations use marked rows, or the current row when none are marked, regardless of column. Cell actions remain cell-scoped. Wildcard pattern rows are non-markable and inspect-only; pattern mutations use the CLI.

Marks survive filtering and refresh for surviving exact targets. Display total and hidden marked counts; visibly remove marks for vanished entries. Clipboard actions use an available platform utility and explain unavailability. Origin opening requires a safely derived HTTP(S) repository web URL; never execute arbitrary origin schemes. Cells do not edit paths, origins or Git state.

### 4.3 Remote discovery

Implementation status: Not started

Support `inventory [--remote] [--include-archived]`; archive inclusion requires remote mode. Use the providers in §3.2. Local results and navigation remain usable while providers load; preserve query/selection and successful partial results, with provider-specific progress and errors.

| Event | Behavior |
| --- | --- |
| Enable remote, including through Add | Fetch enabled providers; remain enabled until explicitly disabled. Cancelling Add does not disable remote. |
| Refresh remote | Explicit menu action refetches all enabled providers; keep successful cached rows visibly stale during loading. |
| Retry | Retry failed providers only. |
| Disable remote | Cancel/invalidate remote requests; hide remote-only rows and visibly remove their marks. Retain local/declaration rows, session cache and archive preference. |
| Change archive preference while enabled | Invalidate remote requests and refetch enabled providers. |
| `R` | Refresh local/config state only, not providers. |

Remote fetching never registers, clones or runs hooks. Deduplicate by identity without collapsing distinct local paths. Bound provider requests to 30 seconds and provider/probe cancellation to 2 seconds; these limits do not time out interactive Git or hook processes.

### 4.4 Actions and eligibility

Implementation status: Not started

Registration changes are identity-scoped; deletion uses the exact selected path. Clone destinations follow configured layout, including when the selected checkout is elsewhere. Preview this difference. Checkout-only operations preserve declarations and exclusions exactly; retained registration lets `ensure` recreate a removed checkout.

| Action | Effect |
| --- | --- |
| `r` Register | Establish effective registration using §3.2; preserve files. |
| `u` Unregister | Remove explicit declarations and exclude from all matching wildcards; preserve files. |
| `c` Clone | Clone at configured destination; a matching checkout is a no-op. |
| `C` Clone + register | Register only after successful/no-op cloning. Config failure does not undo the checkout. |
| `d` Remove | Delete the exact checkout under §3.3 guards; preserve registration. |
| `D` Remove + unregister | Unregister after successful removal, or when a declaration was known missing at invocation and its target remains safely absent. |

| Entry | Registration | Cloning | Removal |
| --- | --- | --- | --- |
| Supported present checkout | Allowed; no-op if already in requested state | Configured destination only; warn if different from found path | Exact found path only |
| Declared, known missing | Allowed | Configured destination | `d` unavailable; `D` only after rechecking absence |
| Remote-only/excluded identity, no checkout | Allowed | `c` preserves exclusion; `C` registers | Unavailable; use `u` |
| Originless checkout | Unavailable until supported origin exists | Unavailable | Unavailable |
| Conflict/unreadable destination | Only from an independently known declaration/reference | Blocked | Blocked |
| Wildcard pattern | Inspect-only | Inspect-only | Inspect-only |

Inspect shows exact paths, registration relationships and diagnostics. A matching clone destination does not suppress `C`'s registration step. Hooks execute only as part of configured clone behavior, not discovery, inspection or registration; explicit reruns use `lager hook`.

### 4.5 Batches, confirmation and state

Implementation status: Not started

- Preview all targets, including hidden marks, and freeze their exact paths and identities at invocation. Refreshes/new arrivals never retarget a batch.
- Run one sequential mutation batch at a time, with per-target config writes and live revalidation. Continue past blocked or failed targets and report each reason; preserve successes.
- Deduplicate shared registration changes while retaining path-specific disk operations. Combined unregister for an identity waits until all selected removals for it succeed; failed, stale, cancelled or unattempted targets prevent it. Preview effects on unselected checkouts' shared registration without touching their files.
- Show action, completed/total, exact active target, cancellation state and per-target outcomes: succeeded, no-op, failed, blocked, cancelled or unattempted. Report disk and config outcomes separately after partial failure; do not imply rollback.

Removal confirmation lists clean targets, force-eligible named losses and hard blockers. Force defaults off; a separate acknowledgment authorizes only the disclosed losses at listed paths. Confirming processes eligible targets; unacknowledged warnings and blockers fail individually. Cancelling confirmation changes nothing.

Immediately before mutation, revalidate ownership, identity, registration consequences and loss classes. Material changes or post-invocation disappearance produce `stale-confirmation`, prevent unregistering that target and do not stop independent targets. Force never authorizes new risks or bypasses §3.3 guards.

Browsing remains available during a batch except when native Git/hooks own the terminal. Suspend the TUI for native output/authentication and restore it afterward. Menu cancellation stops remaining work and safely cancels active background work; during native handoff Ctrl-C interrupts the child/batch and exits `130`. Quitting during a batch offers cancellation or return. Preserve completed outcomes and refresh affected state after cancellation.

Query, cursor, marks and caches are session-only. Refresh explicitly and after mutations; no external filesystem watcher is required. Mark cached results stale, and accept asynchronous observations only for the active source generation and unchanged target/config snapshot.

Normal quit returns `1` if any operational/source failure occurred during the session, otherwise `0`; successful retry does not erase the aggregate outcome. Requested-action blockers and discovery/observation/provider/mutation failures count. Declined confirmation, deliberate cancellation, unavailable optional utilities and informational exclusions do not. Fatal startup/config errors return `1`; invalid invocation or non-TTY use returns `2`.

## 5. Worktree management

Implementation status: Not started

### 5.1 Commands and placement

Implementation status: Not started

```text
lager worktree list [REPOSITORY] [--json]
lager worktree add <REPOSITORY> <NAME> [--branch EXISTING | --new-branch NEW] [--start REF] [--path PATH]
lager worktree remove <PATH> [--yes] [--force]
```

- `list` without an argument uses the cwd repository, not a global scan; outside a repository it requires an explicit target. Include primary and externally created/placed worktrees through native Git.
- A repository argument is a local non-bare checkout path or repository reference resolving to its configured checkout. Linked paths resolve to the primary. Mutations require explicit targets; removal identifies a linked worktree by exact path, not branch.
- `add` defaults to a new branch named `NAME` from the primary's local HEAD. `--new-branch` names it independently; `--branch` selects an existing local branch. `--start` applies only to new branches and must resolve locally to a commit. Reject invalid combinations before mutation; never fetch, reset an existing branch, or override Git's checked-out-branch restrictions.
- Default placement is `<primary>.worktrees/<name>`, beside the primary even when invoked through a linked checkout.
- Optional top-level TOML `worktree_root` uses HOME-relative portability rules: `~`, `~/relative` or HOME-relative, without absolute paths or `..`. It places worktrees at `<worktree_root>/<primary-relative-to-root>.worktrees/<name>`. A primary outside configured `root` requires `--path` when this setting is used.
- `--path` overrides defaults, accepts absolute/cwd-relative paths including deliberate `..`, normalizes to an absolute destination and is never persisted. External destinations are allowed.
- `NAME` is one ASCII component starting with a letter/digit and containing letters, digits, `.`, `_` or `-`; no separators/traversal. Git validates branch names separately. Derived destinations must stay inside their computed container; explicit destinations need not.
- All destinations reject collisions, symlink ancestry and nesting inside a checkout or Git metadata. Even an empty existing destination is a collision. Create ordinary missing parents only after validation.

Worktrees are not declarations and `ensure` does not recreate them. Do not copy environment files, secrets, dependencies or ignored files into new worktrees. Failed creation reports remaining directories, branch and metadata rather than claiming rollback.

### 5.2 Removal safety

Implementation status: Not started

Use native Git worktree removal, never recursive-delete fallback. Verify reciprocal ownership between the exact linked path and common Git directory immediately before removal; no remote origin is required.

Always retain branches. Clean branch-attached commits are not blocked merely because they are unpushed. Detached HEAD must be an ancestor of a commit protected by a retained shared `refs/heads/*`, `refs/tags/*` (peeled to a commit), or `refs/remotes/*` ref. HEAD, reflogs, pseudorefs, per-worktree, stash and replacement refs are insufficient. Failed/unknown reachability proof blocks removal.

Worktree `--force` accepts disclosed dirty/untracked/ignored-file loss only. It never waives ownership, path, lock, primary-checkout or detached-commit protection. Initialized/populated submodules or unknown submodule state are non-forceable blockers; an unpopulated `.gitmodules` declaration alone is not.

Stale/absent paths and locked entries receive diagnostics and explicit native Git recovery guidance, not automatic prune/repair. Repository primary-deletion guards in §3.3 apply independently.

Interactive removal confirms exact path, branch retention and losses, defaulting to no unless `--yes` is supplied. Non-interactive removal requires `--yes`; `--yes --force` explicitly accepts eligible losses. Declining is a skip (`0`); cancellation is `130`. No host integration or process tracking is required.

### 5.3 Output contract

Implementation status: Not started

Human listing shows paths, branch/detached state and lock/prunable information. Mutation commands retain native Git streams and §3.3 exit codes.

`worktree list --json` emits `{schema_version: 1, worktrees: [...], errors: [...]}`. Each record always includes:

| Fields | Contract |
| --- | --- |
| `repository_identity` | Supported normalized origin or null |
| `primary_path`, `path`, `is_primary` | Absolute observed paths and boolean; include primary and external records, sorted by path |
| `branch`, `head` | Full local ref and full Git object ID; null for detached branch or unavailable/unborn values as appropriate |
| `locked`, `prunable` | Independent booleans |
| `lock_reason`, `prune_reason` | Git-provided string or null |

Errors contain `{path, code, error}`; path is string/null, code is `git_failed`, `unreadable` or `invalid_metadata`, and the readable message need not be stable. Sort by path (null first), then code. Retain successful records and repeat readable diagnostics on stderr without contaminating stdout.

Invalid arguments/configuration or unresolved repository fail preflight without JSON. Once resolved, partial or total inspection failure emits the object, including empty records if necessary, and exits `1`. Missing/unreadable facts produce diagnostics, not invented clean records. Success has empty `errors`. This schema is separate from `list --json`.

## 6. Quality and acceptance

Implementation status: Partial

### 6.1 Architecture and interface

Implementation status: Partial

- CLI and TUI repository actions share application services; worktree operations are separate host-independent services. Domain/application logic does not depend on rendering or subprocess mechanics.
- Keep Git, filesystem, providers and config storage as explicit boundaries. Avoid a generic plugin/workflow framework; maintain the public Rust library contract.
- Preserve safe config writes, exact-path revalidation and native output. Pass paths/references as arguments and safely quote intentional shell substitutions.
- Treat hooks as trusted executable configuration; discovery never executes repository-supplied code. Do not store credentials or leak secrets. Sanitize external text against terminal control sequences.
- Bound background requests/probes and cancellation, not inherited interactive Git/hook runtime. Always restore terminal state on exit, interruption, resize and subprocess return.
- At 80×24, preserve navigation/actions with horizontal scrolling, pinned repository identity and full selected-cell details. Support light/dark and no-color presentation with text/symbol status, visible focus, help, empty/loading/error states and confirmation.

### 6.2 Responsiveness and verification

Implementation status: Partial

Use release builds and documented fixtures of 100 and 1,000 repositories, including declared/missing, unregistered, conflicting and unreadable cases. Target p95 ≤250 ms from process start to the first usable frame and p95 ≤50 ms for cached search and input during refresh/delayed-provider loading. First frame is not completed discovery; measure source completion separately.

Record machine, commands, fixture mix, cold/warm process runs and input samples. Use at least 20 runs per startup condition and 100 events per interactive condition, with nearest-rank p95. “Cold” means no Lager session cache, not flushed OS disk caches. Performance claims require measured comparisons; target changes require specification review.

| Acceptance area | Required evidence |
| --- | --- |
| Commands and automation | Binary-boundary tests for repository operations, config, provider errors, native output, exit codes and identical `inventory`/`inv` and `list`/`ls` behavior, including non-TTY use. |
| Discovery and identity | Offline/remote fixtures covering wildcards and exclusions, overlapping patterns, originless/duplicate/nonstandard paths, missing/conflicting/unreadable locations and excluded worktrees/submodules. |
| TUI | Real PTY keyboard tests for cells, `/` search, hidden marks, refresh, independent/combined actions, optional utilities and terminal restoration; visual fixtures support behavioral assertions. |
| Batches and safety | Cancellation without mutation, per-target continuation, disk/config partial success, shared-identity unregister guards, stale confirmation, changed origin/path/config and scoped force. |
| Asynchronous state | Slow/failed providers, retries/toggles, stale responses, disappearing targets and honest pending/error state without losing usable local results. |
| Worktrees | Real temporary Git repositories covering branch modes, placement overrides, collisions, external/originless ownership, retained refs/branches, locks/stale metadata, submodule blockers, force and JSON failures. |
| Delivery | Linux/macOS x86_64/ARM64 builds; formatting, warning-denying Clippy and locked all-target tests; release archive checksums/provenance; Cargo/Mise/archive installation; correct versions in development, tags and source archives. |

Use isolated HOME/config roots, state-based waits and retained failure diagnostics. Release requires these acceptance checks, updated help/config/JSON documentation and approved visual fixtures. Test plans define harness details without changing product behavior.

## 7. Scope boundaries

Implementation status: Not applicable

Lager 1.0 excludes:

- Forklift, terminal-host integration and local destination/shell launching.
- Worktree entries or submodule management in inventory; adoption/moving of misplaced checkouts.
- Inline cell editing, branch switching, staging, merge/rebase or general Git management.
- Declarative worktrees, worktree setup hooks, move/lock/prune/repair/branch-delete commands, `wt` alias and batch worktree commands.
- Per-repository worktree placement templates, automatic copying of environment/dependency files, or repository-provided setup execution.
- Inventory-specific hook reruns, combined inventory JSON, persisted UI state, daemons and additional providers beyond §3.2.
- Automatic pulling/resetting during reconciliation, web/cloud/multi-user features, telemetry and enterprise identity/audit systems.
