# Lager 1.0.0 product requirements

Status: draft for Nik's review. Implementation is not approved by this document's creation.

## 1. Product goal

Lager manages a developer's local Git repositories and helps them start working in the right checkout, worktree, or Herdr destination.

Version 1.0 combines declarative repository management with an interactive repository inventory, local worktree management, and a clean implementation of helm.herdr's functionality under `lager forklift`.

Nik is the primary user. This is a personal project without external users to migrate. Prefer a small, understandable implementation over speculative extension points or compatibility machinery. Existing useful behavior is the baseline; breaking changes require an explicit reason and review.

### Reading this draft

- **Existing:** behavior present in the inspected Lager or helm.herdr source. Preserve it unless a change is explicitly approved.
- **Agreed:** scope or behavior Nik selected during the PRD discussion.
- **Proposed:** requirements and acceptance criteria offered for review, not settled decisions.
- **Open:** a decision that affects implementation and needs resolution.

Requirements below are proposed unless identified as existing or agreed. The open-decision section makes the remaining choices explicit.

### Agreed scope

| Area | Scope |
| --- | --- |
| Repository management | Include the complete current Lager feature set. |
| Inventory | Add `inventory`, alias `inv`, as a persistent interactive view that refreshes after actions. |
| Listing | Preserve `list` and add the `ls` alias. |
| Inventory sources | Show declarations and local checkouts by default. Remote discovery is opt-in through `--remote` or the Add flow. |
| Inventory actions | Inspect state, register, unregister, add and register, remove and unregister. |
| Forklift | Absorb helm.herdr's functionality into v1 through a clean rewrite under `forklift`. |
| Worktrees | Provide a standalone command tree and shared application services that forklift can use. |
| Worktree persistence | Manage local working copies, not declarations that `ensure` recreates. |
| Worktree placement | Default to a sibling container, for example `~/repos/nikbrunner/lager.worktrees/<name>`. Placement is configurable. |
| Rewrite quality | Proper TUI end-to-end tests, performance improvements supported by measurements, and modest interface/color improvements. |

V1 includes interactive terminal interfaces. Inventory is the collection-management view; forklift is the navigation and working-context view. They share repository and worktree operations rather than implementing separate management rules.

## 2. Terms and ownership

| Term | Meaning |
| --- | --- |
| Repository identity | The normalized host and repository path used to compare repository references. |
| Declaration | Portable configuration describing a repository, or a wildcard set, that Lager should keep available. |
| Checkout | A concrete local working directory. An identity can have more than one checkout path. |
| Primary checkout | The main working directory associated with a Git repository's linked worktrees. |
| Worktree | An additional local working directory managed through native Git worktree operations. |
| Inventory entry | A declaration, discovered checkout, or remotely discovered repository presented with its known state. |
| Destination | Something forklift can open or focus: a checkout, worktree, Herdr workspace/tab/pane, agent, directory, remote, or integration action. |
| Workspace | A Herdr workspace. It is distinct from a Git worktree. |

Lager owns repository declarations, local repository operations, worktree operations, and its interface state. Git owns Git metadata and worktree bookkeeping. Herdr owns terminal workspaces, tabs, panes, and focus.

Registration does not imply a checkout exists. Closing a workspace does not delete its checkout. Removing a worktree does not implicitly delete its branch.

## 3. Existing Lager feature baseline

The CLI, configuration and output references remain the detailed baseline. This section records the complete feature families to carry into v1.

### 3.1 Commands

| Command | Existing behavior to preserve |
| --- | --- |
| `init` | Create configuration once; select the repository root; optionally create it and configure GitHub. Interactive defaults are `repos`, create the root, and configure GitHub. Missing optional tools produce diagnostics without blocking initialization. |
| `register [REPOSITORY]...` | Declare concrete repositories or trailing wildcards. Support optional post-clone hooks on explicit declarations and archive filtering during discovery. |
| `unregister [REPOSITORY]...` | Remove explicit declarations or exclude concrete members from matching wildcards. Leave local files untouched. |
| `add [REPOSITORY]...` | Clone repositories with an explicit or interactive registration choice. A matching existing checkout is a no-op. `--post-clone` implies registration. Successful clones remain available when other items or hooks fail. |
| `remove [REPOSITORY]...` | Permanently delete validated standalone checkouts. Support unregister/keep-registered choices, confirmation, and bounded `--force` behavior. Update declarations only after successful deletion or confirmed absence. |
| `ensure` | Sequentially create missing effective declarations. Do not pull, reset, or otherwise update existing checkouts. Continue through individual failures and report aggregate failure. |
| `hook [REPOSITORY]...` | Explicitly rerun hooks on declared repositories. Report when a selected declaration has no hook. |
| `list` | Report declarations and local state without mutation. Default to offline output; support remote wildcard expansion, archive filtering and stable JSON. |

Existing options and prompts are specified in [CLI reference](../reference/cli.md). V1 adds `ls` as an alias with identical arguments, output and exit behavior.

### 3.2 Repository references and discovery

Existing capabilities:

- Canonical host/path identities, GitHub shorthand, and SCP, SSH, HTTP(S), and file clone URLs.
- Normalized comparison for duplicates, origins and destinations while preserving the configured clone URL text.
- GitHub discovery through authenticated `gh`.
- Bitbucket Cloud and Bitbucket Data Center discovery with configured credentials.
- Provider pagination, archived-repository filtering, and partial-success reporting.
- Provider prefixes and destination layout rules, including custom-host handling.
- Trailing wildcard declarations, exclusions, and explicit-declaration precedence.

Native Git retains responsibility for authentication and transport behavior. Provider tokens remain environment references rather than stored secrets.

### 3.3 Configuration and persistence

Existing capabilities:

- Config precedence: `--config PATH`, `LAGER_CONFIG`, then the HOME-derived default.
- Portable TOML with a HOME-relative root and validated provider-relative paths.
- Explicit declarations, wildcard exclusions and explicit-repository hooks.
- Validation before external operations; unknown-key warnings with unknown content preserved during writes.
- Symlink-aware config resolution, atomic replacement of the target, permission preservation and mutation locking.

New worktree and forklift settings must use the same safe config store where they belong to Lager configuration. Machine-specific observations, recent destinations, pins and host IDs belong in local state rather than portable repository declarations.

See [configuration reference](../reference/config.md).

### 3.4 Automation and process behavior

Existing capabilities:

- Non-interactive invocations never prompt and require the relevant explicit choices.
- Explicit repository arguments bypass selection. Existing omitted-argument selectors support multi-selection.
- Native Git and hook output remains visible, including credential prompts and errors.
- `list --json` emits one versioned JSON object; diagnostics stay on stderr.
- Exit statuses distinguish success/no-op/skip (`0`), operational failure (`1`), usage error (`2`) and interaction cancellation (`130`).
- `list` states are `missing`, `cloned`, `conflict` and `unreadable`; offline wildcard rows remain patterns rather than invented concrete memberships.

The current picker uses external `fzf`. Whether existing selection prompts should use the new interface is open; a new renderer alone does not authorize changing their behavior.

### 3.5 Platforms and distribution

Existing baseline:

- Linux and macOS, x86_64 and ARM64.
- Release archives, Mise installation, Cargo source installation and local Cargo development installs.
- Formatting, warning-denying Clippy, and locked all-target tests in macOS/Linux CI.
- Release artifact checks, checksums and provenance.

Version output and release-context tests must work for development builds, tagged releases and source archives. User-owned version changes are separate from this PRD and must be assessed against the final source state before implementation planning.

## 4. Inventory

### 4.1 Purpose and entry points

**Agreed:** `lager inventory` and `lager inv` open the same persistent interface. Moving between entries and performing actions does not require restarting the command.

Inventory answers: What do I have here, what have I declared, what is missing, and what do I want to change?

`list` remains the non-interactive reporting command. Its existing `--remote` means wildcard expansion; inventory's `--remote` also introduces provider-catalog candidates. Help must explain this difference.

### 4.2 Sources and state

**Agreed:** the default view combines declarations with local checkouts discovered under the configured repository root. It works without a provider request.

Proposed requirements:

- Include explicit declarations whose checkout is missing.
- Include unregistered local checkouts, retaining their exact paths.
- Distinguish explicit registration, wildcard coverage, exclusions, and unregistered entries where that relationship can be established offline.
- Keep unresolved wildcard declarations visible without pretending their remote membership is known.
- Merge a declaration and its matching checkout into a useful row while preserving separate checkout locations for duplicate origins.
- Distinguish registration state from local checkout state. Conflicts and unreadable locations must not appear as missing repositories eligible for an unchecked clone.
- Recognize linked worktrees as worktrees. Do not offer standalone recursive repository deletion for them.
- Keep additional non-Git directory sources in forklift rather than treating them as repository inventory.

Open: discovery depth, nested repositories, checkouts without an origin, arbitrary checkout locations, and the presentation of worktrees and wildcard rows.

### 4.3 Remote discovery

**Agreed:** `inventory --remote` enables provider discovery. The Add flow also offers remote discovery without requiring users to restart inventory.

Proposed requirements:

- Display local results while remote loading continues.
- Show a loading indicator and the provider currently loading. Use counts when available; do not show fabricated percentages.
- Update results without discarding the query, current location or selection.
- Merge remote candidates by repository identity without collapsing distinct local paths.
- Identify partial provider failures and retain successful and local results.
- Support retry and cancellation; leaving the view must not leave background work running indefinitely.
- Fetching a catalog never registers or clones anything by itself.
- Apply archive filtering consistently with existing discovery, with the exact inventory flag/filter contract documented before implementation.

### 4.4 Interaction

Proposed requirements:

- Fuzzy search, keyboard navigation, visible action hints and contextual help.
- Separate columns for repository/path, registration, and local availability or problem state.
- Preserve query and selection through refresh where the selected entry still exists.
- Explain unavailable actions rather than letting them silently do nothing.
- Show operation progress, failures and completed actions without losing access to the collection.
- Restore terminal state on normal exit, cancellation, subprocess handoff and failure.
- Reject interactive mode outside a terminal with actionable guidance to use explicit commands or `list`.

Exact keybindings, bulk actions, column layout, Git branch/dirty-state columns and the renderer are open decisions.

### 4.5 Actions

| Action | Required outcome |
| --- | --- |
| Inspect | Show the reference, exact known path, registration relationship, local state and reason for any conflict. |
| Register | Add a declaration without cloning or moving a checkout. Explain when registration will point to a different configured destination. |
| Unregister | Remove the declaration or add the relevant wildcard exclusion; preserve checkout files. |
| Add and register | Clone an explicit reference or chosen remote candidate and register it through existing services. Keep successful work visible after partial failure. |
| Remove and unregister | Confirm the exact target and deletion consequences, enforce existing safety checks, then unregister only when disk removal succeeds or the target is absent. |
| Refresh | Re-read state without clearing the user's browsing context. Remote refresh is explicit when remote discovery is disabled. |

Checkout-only addition, removal while keeping registration, hook reruns and opening a destination from inventory are proposed convenience actions, not yet agreed additions.

### 4.6 Acceptance journeys

1. Open offline inventory with declared/cloned, declared/missing, unregistered and conflicting fixtures; distinguish each without a network call.
2. Register and unregister an existing checkout while remaining in the view; observe updated state and preserved files.
3. Add a remote repository with registration; return to an updated local entry.
4. Cancel removal and observe no filesystem or config mutation.
5. Complete safe removal and unregister; reject an unsafe target even when the UI requests force.
6. Load two providers where one fails; keep local and successful remote entries usable.
7. Refresh after an external filesystem or config change; revalidate actions against current state.

## 5. Forklift

### 5.1 Purpose and rewrite contract

**Agreed:** `lager forklift` provides helm.herdr's feature set through a clean implementation in Lager. Worktree management is accessible from forklift through the same application services as the standalone command tree.

The rewrite is motivated by a clearer product goal and code structure. There is no currently identified user-facing workflow defect that justifies a wholesale interaction redesign. Preserve useful behavior, measure responsiveness, and improve presentation modestly.

The baseline is the inspected helm.herdr source, not unverified documentation claims or an obligation to preserve every internal abstraction. Any deliberate feature omission or behavior change requires review.

### 5.2 Feature parity checklist

The following are **existing helm.herdr capabilities** to account for in v1:

| Area | User-facing scope |
| --- | --- |
| Entry points | Direct picker invocation, Herdr-managed popup, persistent side-pane toggle/focus behavior, jump-back action and a non-interactive candidate/debug listing. |
| Live topology | Workspace → tab → pane navigation and exact focus at the selected depth, including exact pane IDs. |
| Search and filtering | Fuzzy queries, source filters, normal/search modes, keyboard help, word deletion, query/filter reset, and configurable source shortcuts. |
| Query semantics | Agent-only selection and agent-name, status/workspace and path searches, including current `agent`, `!name`, `@status` and `/path` conventions. |
| Agents | Agent destinations, status indicators, aliases and configurable ordering. |
| Workspace opening | Focus/reuse an existing workspace or create one for the selected directory/project, respecting configured ordinary-open behavior. |
| Workspace closing | Close the matching open workspace, protect the workspace hosting the picker, and refresh state. |
| Projects | Discover Herdr Plus project files and apply their tabs, splits, labels and commands. |
| Directory templates | Apply a configured Herdr Plus template to a directory, including appending template tabs to an existing workspace when explicitly requested. |
| Directory sources | Zoxide history and configurable depth-limited filesystem roots, including non-Git project directories. |
| Remote targets | Configured Herdr remote handoff. |
| Quick Actions | Delegate to the Herdr Plus Quick Actions interface. |
| Command integrations | Configured collection commands returning JSON and configured open actions with safely quoted substitutions. |
| Pins and history | Mark/unmark destinations without duplicates; local jump-back history; optional previous-workspace presentation; stale-target handling. |
| Worktree context | Observe worktree/repository/branch relationships for open destinations, including detached HEAD labels. |
| Presentation | Source/status labels, topology and flat-result views, Herdr theme inheritance, notification controls and optional sound. |
| Preferences | Source enablement/order, ranking preferences, fuzzy-engine choices and existing picker behavior settings. |
| Update workflow | Background update notification and user-confirmed installation behavior; the delivery mechanism must be reconciled with Lager's release/install methods. |

The source does not establish working built-in local-session attachment despite broader README language. Do not silently promise it as parity. External integration results with session-like kinds and configured remote targets are part of the observed behavior.

Parity review must also resolve source/documentation differences around workspace identity and template behavior. Preserve intended workflows rather than copying accidental label conventions or silent failures.

### 5.3 Lager and worktree integration

Proposed requirements:

- Offer Lager checkouts and their worktrees as destinations alongside the existing forklift sources.
- Open the selected concrete checkout/worktree, not a guessed path from its repository name.
- Make registered-but-missing repositories distinguishable; cloning before opening requires an explicit action.
- Allow worktree creation and safe removal through shared services. Opening a newly created worktree is an explicit navigation choice.
- Deduplicate repeated references to a destination while retaining action-relevant distinctions such as project layout application.
- Revalidate stale workspace/pane targets and refresh instead of focusing an unrelated replacement.
- Show missing Herdr or optional-provider capabilities without breaking repository commands or worktree commands.
- Preserve the popup's close-on-navigation and side pane's stay-open workflow where applicable.

Open: whether all repository mutation actions are also exposed in forklift, or whether it links users to inventory for collection management.

### 5.4 Integration boundaries

- Repository and worktree services do not depend on Herdr or terminal rendering.
- Herdr integration uses a defined CLI/socket boundary with a documented supported version range.
- Optional sources are isolated: missing tools are understandable, and one failing source cannot freeze the whole picker.
- External command sources remain trusted user configuration. Arbitrary repository content must not become an executable integration automatically.
- Project bootstrap and template actions report partial failure and any created terminal structure. Repeating an action must not silently duplicate structure unless duplication is the documented operation.
- Plugin installation, action IDs, configuration ownership and updater behavior need one consistent Lager delivery contract.

## 6. Local worktree management

### 6.1 Model and command surface

**Agreed:** worktrees are local working copies. They are not portable declarations and `ensure` does not recreate them. Defaults for worktree behavior may still live in portable configuration.

**Agreed:** provide standalone commands that use the same application services as forklift. Herdr is not required for them.

Proposed command shape, subject to naming review:

```text
lager worktree list [REPOSITORY] [--json]
lager worktree create <REPOSITORY> <NAME> [branch and destination options]
lager worktree remove <WORKTREE> [confirmation options]
```

This is a product sketch, not approved CLI syntax. `wt`, `add` versus `create`, branch flags, and selectors remain open.

Proposed minimum behavior:

- Discover worktrees through native Git, including ones created outside Lager.
- List exact paths, branch or detached state, and locked/prunable state where available.
- Create a worktree for an existing branch or a new branch from an explicit starting point.
- Respect Git's restrictions on checking out a branch in multiple worktrees.
- Identify worktrees by concrete path or another unambiguous selector, not branch name alone.
- Safely remove a worktree using native Git bookkeeping.
- Preserve branches by default; branch deletion is a separate explicit decision.

Move, lock/unlock, prune/repair, branch deletion and batch worktree operations are open scope choices rather than implied promises.

### 6.2 Placement and configuration

**Agreed default:** for `~/repos/nikbrunner/lager`, create named worktrees under:

```text
~/repos/nikbrunner/lager.worktrees/<name>
```

The container is beside the primary checkout. It is not inside its tracked files.

Proposed requirements:

- Configuration controls default placement; a creation-time destination override handles exceptions.
- Persist portable settings, not expanded machine-specific absolute paths.
- Derive sibling placement from the primary checkout even when invoked from an existing linked worktree.
- Validate names and paths, reject traversal and unsafe symlink targets, and refuse collisions rather than overwrite directories.
- Keep worktree names distinct from branch names so `feature/topic` need not implicitly create nested directories.
- Identify externally placed worktrees through Git metadata even when outside the configured default placement.

Open: supported placement modes, global versus per-repository overrides, naming rules, and the approved roots for explicit destinations.

Additional configuration candidates, not yet agreed:

- Default starting-reference policy for new branches.
- An opt-in post-create setup command, separate from post-clone hooks.

Do not copy ignored files, credentials, dependency directories or environment files by default. Any such automation requires an explicit contract and trust decision.

### 6.3 Lifecycle safety

Proposed requirements:

- Preview the exact worktree path and branch before destructive operations.
- Check dirty and untracked files, detached/local-only work, locks and repository identity before removal.
- Distinguish removing a worktree directory from deleting a branch and closing a Herdr workspace.
- Guard primary-checkout deletion when linked worktrees depend on its Git metadata. This affects the existing repository `remove` service as well as the new commands.
- Never fall back to generic recursive directory deletion when a Git worktree operation fails.
- Handle already-removed paths and stale bookkeeping with clear diagnostics and an explicit recovery path.
- Report what exists after a failed creation or setup hook. Preserve user work and successful outcomes; do not claim rollback unless it occurred.

The exact force policy, detached-commit protection and interaction with open Herdr workspaces require approval before implementation.

### 6.4 Acceptance journeys

1. Create a new-branch worktree in the sibling layout through the CLI and observe it in forklift.
2. Open it in Herdr, then invoke opening again and reuse the correct workspace.
3. Discover a worktree made directly with Git, including an explicit external destination.
4. Reject a destination collision or invalid path without changing the repository.
5. Reject removal of a dirty or locked worktree under the normal safety policy.
6. Cancel removal and preserve files, Git metadata and branch.
7. Remove a clean worktree through Git and retain its branch.
8. Attempt to remove its primary checkout while dependent worktrees exist; preserve dependent work and report the blocker.

## 7. Interface, performance and implementation quality

### 7.1 Visual direction

**Agreed:** improve the interface and colors slightly. Preserve the current useful workflows rather than assume a new interaction model is needed.

Proposed acceptance criteria:

- Focus, selection, registration, Git state and agent state are visually distinguishable.
- Text or symbols accompany status colors.
- Light/dark and inherited Herdr palettes remain readable, including focused and selected rows.
- Long paths and labels truncate predictably without obscuring which destination will be acted on.
- Narrow terminals and resize events preserve navigation and action access.
- Inventory and forklift use consistent meanings for shared statuses and destructive actions.
- A small set of approved visual fixtures covers normal, search, loading, empty, error and confirmation states.

Exact palettes and layout changes need visual review. This PRD does not select a terminal UI library or require a custom theme engine.

### 7.2 Responsiveness

**Agreed:** seek a faster interface. Performance improvement must be demonstrated rather than inferred from a rewrite.

Measure the existing helm.herdr release build and the replacement on the same machine and representative data:

| Measurement | What to record |
| --- | --- |
| Cold and warm opening | Time until the first usable frame and until relevant sources are ready. |
| Search | Keystroke-to-result latency as candidate counts grow. |
| Refresh | Time to updated state and whether input remains responsive. |
| Open/focus | Time from activation to the intended Herdr destination. |
| Background activity | Idle CPU, subprocess frequency and unnecessary redraws. |
| Expensive sources | Git worktree probes, filesystem traversal, provider discovery and external collection commands. |

Proposed requirements:

- Slow sources do not block input or local-result rendering.
- Typing and ordinary redraws do not trigger full filesystem scans, provider requests or repeated Git probes.
- Source work has bounded execution/cancellation behavior and cannot overwrite newer results with stale ones.
- Refresh preserves useful cached results while showing their loading/error state honestly.
- Measure release builds with recorded fixture sizes, hardware and commands.

Numeric latency and resource budgets are open until a baseline is recorded. Agree them before performance implementation and release acceptance. At least one measured bottleneck should improve, with no material regression in the other agreed journeys; if no bottleneck is demonstrated, revise the improvement claim rather than fabricate one.

### 7.3 Code structure

- Inventory, forklift and explicit commands use the same application operations for repository and worktree mutations.
- Domain and application services remain independent of terminal rendering and subprocess mechanics.
- Treat filesystem, Git, config storage, provider discovery, Herdr and external sources as explicit boundaries.
- Separate source loading, state updates, rendering and action execution enough to test them independently.
- Prefer concrete modules around these responsibilities over a general plugin framework or configurable workflow engine.
- Preserve public Rust library behavior or document approved changes; CLI stability alone is not the whole library contract.

## 8. Testing and security acceptance

### 8.1 Test layers

**Agreed:** proper end-to-end tests for the rewritten TUI are a v1 requirement.

| Layer | Required evidence |
| --- | --- |
| Binary-level repository tests | Existing command contracts plus inventory/worktree outcomes, using isolated HOME/config roots and real temporary Git repositories. |
| PTY interface tests | Launch the actual Lager binary in a terminal, send real key sequences, inspect rendered state, and verify resulting filesystem/config/Git state. |
| Deterministic Herdr boundary tests | Controlled CLI/socket responses for exact focus, reuse/create, topology changes, delays and failures. These are integration tests, not proof of real Herdr compatibility. |
| Real Herdr end-to-end tests | Run the plugin and binary against a supported Herdr version in an isolated session; exercise popup, side pane, topology focus, workspace creation/reuse, jump-back and worktree opening. |
| Visual fixtures | Review representative terminal layouts and palettes; use snapshots as support, not as the only behavioral assertion. |
| Performance fixtures | Repeatable commands and datasets for the agreed responsiveness measurements. |

Prefer event/state-based waits over fixed sleeps. Failures should retain terminal output, relevant process logs and the fixture state needed to diagnose them. Real Herdr checks must be repeatable even if host constraints require a dedicated acceptance environment rather than every CI job.

### 8.2 Required interface scenarios

- Startup, normal/search mode, filtering, keyboard help and an empty result set.
- Stable selection across refresh, disappearing targets and stale asynchronous results.
- Repository registration/addition/removal, including cancellation and partial failures.
- Worktree creation, opening and guarded removal through forklift.
- Exact workspace/tab/pane targeting and agent navigation.
- Popup versus persistent side-pane behavior and owner-workspace close protection.
- Pins, jump-back, remote handoff and configured integration actions.
- Project/template behavior, including intentional appending and bootstrap failure.
- Missing optional tools, malformed source output, unavailable Herdr and slow sources.
- Terminal resize, narrow layouts, long/Unicode names and terminal control characters in external text.
- Ctrl-C, ordinary exit, child-process failure and terminal restoration.
- Native Git authentication/output handoff without a corrupt terminal or inaccessible prompt.

### 8.3 Data-loss and trust boundaries

These are local-tool protections, not a multi-user security platform:

- Preserve existing config locking, symlink handling, atomic writes and permissions.
- Revalidate destructive targets immediately before mutation, retaining exact paths throughout selection and execution.
- Test duplicate origins, mismatched origins, symlink replacement, path traversal, linked worktrees and config changes during a session.
- Keep force narrowly defined; it cannot waive repository identity or filesystem-boundary checks.
- Pass paths and references as subprocess arguments. Quote substitutions in intentionally configured shell commands.
- Treat hooks, templates and integration commands as trusted executable configuration; do not execute code merely because a repository or remote result was discovered.
- Do not store credentials in declarations or expose secrets in diagnostics.
- Render external labels as text, preventing embedded terminal control sequences from changing terminal behavior.
- Report malformed configuration and source failures rather than silently replacing user preferences with defaults.
- Bound external process waits and preserve successful outcomes when another source or action fails.

Dependency checks and release-artifact verification are proportionate additions. Enterprise identity, audit-log systems and telemetry are outside this personal project's v1 scope.

## 9. Delivery and release criteria

A proposed release checklist:

- [ ] Existing Lager commands, configuration and automation contracts have a checked feature matrix with approved deviations called out.
- [ ] Inventory's agreed offline, persistent-action and remote-discovery journeys pass.
- [ ] The helm.herdr parity checklist is exercised against the rewritten forklift; omissions are explicitly approved.
- [ ] Worktree commands and forklift use shared services and pass real-Git safety tests.
- [ ] PTY tests and real Herdr acceptance tests pass in documented environments.
- [ ] Performance baselines, budgets and comparison results are recorded.
- [ ] Visual fixtures and shared color/status meanings are approved.
- [ ] Supported Herdr versions, plugin installation, action IDs and configuration/update ownership are documented and tested.
- [ ] CLI help, configuration reference, JSON schemas, automation instructions and human test instructions cover the release.
- [ ] Linux/macOS checks and supported release artifacts pass; version output is correct across build contexts.
- [ ] Nik's current helm.herdr configuration has an explicit, tested transition path that does not destroy the original setup.
- [ ] No release-critical product or safety choice remains unresolved.

Implementation can be split into independently reviewable slices: baseline contracts, shared inventory state, worktree services, inventory UI, forklift parity, then integration/performance/visual acceptance. This is sequencing guidance, not an implementation plan or permission to start coding.

## 10. Open decisions and optional improvements

### 10.1 Decisions required before implementation of the affected area

| Decision | Why it matters |
| --- | --- |
| Discovery boundaries | Depth, nested repositories, missing origins, duplicate paths and linked-worktree presentation determine inventory correctness. |
| Registration of nonstandard checkouts | The current declaration layout may point somewhere other than the discovered checkout. Decide between explicit diagnosis, adoption/move support, or a reviewed config extension. |
| Offline wildcard representation | Separate known local coverage from remote membership that has not been fetched. |
| Inventory interaction details | Approve columns, keybindings, bulk actions, additional convenience actions and archive filtering. |
| Renderer and existing selectors | Choose the smallest implementation that satisfies persistent interaction and tests; decide whether existing fzf prompts change. |
| Forklift/repository action overlap | Define which management actions appear in forklift versus inventory. |
| Worktree command/config schema | Approve naming, selectors, branch creation defaults, placement modes and override precedence. |
| Worktree safety policy | Approve force, detached work, branch deletion, locked/prunable entries and primary-checkout removal behavior. |
| Open-workspace handling | Decide whether removing a worktree with an open Herdr workspace blocks, warns or offers explicit close-and-remove. |
| Worktree setup automation | Decide whether a post-create hook belongs in v1 and how it is scoped. |
| Helm parity exceptions | Resolve local-session claims, project/directory identity and template semantics against actual desired behavior. |
| Forklift preferences | Decide whether all fuzzy engines/ranking controls remain useful; do not silently remove existing choices. |
| Plugin and configuration transition | Set action IDs, supported Herdr versions, config/state import and old-plugin coexistence behavior. |
| Update ownership | Reconcile plugin updates with Lager installations through Cargo, Mise and release archives. |
| Performance and visual targets | Agree measured budgets and review the proposed visual changes. |
| Machine-readable additions | Decide JSON contracts for worktrees, combined inventory and forklift diagnostics without silently changing `list --json`. |

### 10.2 Small improvements worth considering

These are suggestions, not release commitments:

- A read-only diagnostics command showing configuration, tools, provider access and Herdr compatibility without exposing secrets.
- Branch and dirty/untracked indicators loaded on demand for visible entries.
- A copy-path action and direct opening of a repository's remote URL.
- A combined inventory JSON view useful to shell tooling and future integrations.
- An explicit stale-worktree repair/prune workflow built on Git, with a preview.

### 10.3 Outside the agreed v1 scope

- Declarative worktrees recreated by `ensure`.
- General branch/merge/rebase management or replacing native Git.
- Automatic pulling, resetting or branch deletion during repository reconciliation.
- A web UI, cloud service, multi-user platform, or support for additional terminal multiplexers.
- Automatic execution of repository-provided setup scripts or copying secrets into worktrees.
