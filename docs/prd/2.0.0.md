# Lager 2.0.0 product specification

Lager 2.0 opens a checkout or a worktree as a terminal session with your usual tabs and panes, and takes you back to that session when it exists. Lager keeps the list of repositories and worktrees, so it is the place to start a session for one of them.

It is for someone who works across many repositories and worktrees in [Rex](https://www.superlogical.com/), and for the coding agents that work beside them. A person wants to land in the session and keep going. An agent wants a session it can work in without moving anyone's view.

Companion: [1.0 product requirements](1.0.0.md). Each part's status line tracks what is built: **Not started**, **Partial** or **Implemented**.

## Terms and ownership

| Term | Meaning |
| --- | --- |
| Session | A terminal session in the host, with tabs and panes, opened for one checkout. "Session" means this everywhere in lager. |
| Terminal host | The terminal program that holds sessions. Rex is the one lager supports. |
| Layout | The tabs and panes a new session starts with, from the configuration. |
| Label | The name the host shows for a session. |

Lager owns the record of which session it opened for which checkout, kept on this machine. The host owns its sessions, tabs, panes and focus. Git owns worktrees.

## Principles

- **Optional:** sessions exist only once the configuration has a `[session]` section. Without it lager behaves as a repository manager alone, never calls the host, and shows nothing about sessions.
- **One host at a time:** the configuration names the host. The part of lager that talks to it is small, so another host can be added later without changing the rest.
- **Found by record:** lager finds its own sessions through the record, so a label can be edited in the host afterwards. A session lager did not create is unknown to it, and lager opens its own.
- **Explicit on the command line, default in the inventory:** agents and scripts call the commands, so a command touches a session only when it is asked to. In the inventory someone sits in front of the screen, so opening and closing the session is the default there.
- **Nobody's view moves without asking:** only `open` changes what Rex shows. Everything an agent uses leaves the view alone.
- **A refused removal ends nothing:** a session closes only after its worktree was removed.

## Configuration

The `[session]` section names the host and one layout called `default`, which every repository uses. The layout has the shape of Helm's layout configuration, so a Helm layout moves over once its tables sit under `session.`. A layout lists tabs, each starting with one pane that splits into more. Every pane starts in the checkout.

Labels follow one convention: the repository's directory name for a primary checkout (`lager`), and the repository with the worktree's name in words for a worktree (`lager · Rex integration`).

## 1. Session commands

Implementation status: Implemented. The acceptance steps that move the Rex view are open in the [human checklist](../../HOW_TO_TEST.md#sessions).

Lager works as a sessionizer from the shell.

```sh
lager session open   nikbrunner/lager
lager session open   .
lager session create nikbrunner/lager rex-integration --json
lager session close  nikbrunner/lager rex-integration
lager session list
```

- `open` creates the checkout's session with the configured tabs and panes and switches Rex to it. A second `open` takes you to the same session.
- `create` does the same without switching. With `--json` it returns the session and its panes by name, which is what an agent needs to start work in a pane.
- `close` ends the checkout's session.
- `list` shows the checkouts that have a session.

A repository reference names its primary checkout. A path names the checkout or worktree it lies in. A second argument names a linked worktree by its directory.

If Rex is not installed or not running, these commands say so in one line and exit `1`. Every other lager command is unaffected.

## 2. Worktree flags

Implementation status: Implemented. The acceptance step that moves the Rex view is open in the [human checklist](../../HOW_TO_TEST.md#sessions).

Starting a topic is one command, and so is finishing it.

```sh
lager worktree add nikbrunner/lager rex-integration --open-session
lager worktree add nikbrunner/lager rex-integration --create-session --json
lager worktree remove ~/repos/nikbrunner/lager.worktrees/rex-integration --close-session
```

- `--open-session` creates the worktree and takes you into its session.
- `--create-session` creates it and leaves your view alone, for agents. With `--json` the answer includes the session.
- `--close-session` closes the session once the worktree was removed. A refused removal leaves the session running.

The flag carries the verb, so a reader of a script sees what happens to the session. Without a flag the worktree commands leave sessions alone. A session flag without a `[session]` section is an error before lager creates or removes anything. When the worktree step succeeds and the session step fails, the command says which part happened and exits `1`.

The worktree list shows which worktrees have a session.

## 3. Sessions in the inventory

Implementation status: Implemented. The acceptance steps that move the Rex view or need eyes are open in the [human checklist](../../HOW_TO_TEST.md#sessions).

The inventory is the picker. A mark before a repository's name shows that its primary checkout has an open session. `s` on a row opens the session or jumps to it, then the inventory closes and prints one line naming the session. The menu offers the same as "Open session".

If the session cannot be opened, the inventory stays open and says why. With Rex missing or stopped it says so once, and `s` repeats the reason. A missing or stopped Rex is a notice: it is not a problem and does not change the inventory's exit status, the same as other optional tools. A call that fails on a running Rex is a problem.

Without a `[session]` section none of this is visible.

The inventory's list of failures is called "Problems". `s` belongs to sessions, and an `s` configured for another action wins over it. Column sorting, issue #24 "Sort the inventory table by column", uses `o` and `O`.

## 4. Lean popups

Implementation status: Not started

Every popup in the inventory holds what you act on: a title, the table or list, and one row of key hints inside the popup. A rule is stated when it applies, as the one line you get after pressing the key, and in Help. While a popup is open, the bar at the bottom of the screen shows status only, so the hints appear once.

Text that says what you are about to lose stays:

- the losses of a removal and their acknowledgment
- the typed name and the permanence line of a GitHub delete
- lock states
- the outcome of a batch

## 5. Sessions in the Worktrees popup

Implementation status: Not started

The Worktrees popup shows a mark for each worktree with an open session, and `s` opens the selected one.

Creating a worktree from the popup opens its session afterwards and closes the inventory. Removing one closes its session once the removal succeeded. Both defaults show as a ticked line in the confirmation, `[x] Open session` or `[x] Close session "<label>"`, and `s` switches it off for that run. A removal that is blocked leaves the session open and says so. Without a session, or without a `[session]` section, the line is absent.

## Later

The configuration is shaped so that both of these only add keys:

- Layouts per repository, organization or wildcard, chosen on a repository declaration.
- Programs started in a pane.

## Out of scope

- A second terminal host.
- Recognizing sessions that lager did not create, including the ones Helm made.
- Opening a checkout in an editor or Finder.
- Writing the `[session]` section through `lager init`.
- Column sorting itself.
- Changes to Helm.
