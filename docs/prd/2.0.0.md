# Lager 2.0.0 product direction

Status: high-level direction, not an implementation specification. Forklift is reserved for 2.0; detailed scope and behavior will be revisited after using 1.0.

Companions: [1.0 product requirements](1.0.0.md) · [exploratory forklift concepts](2.0.0-concepts.html).

## Goal

Add `lager forklift`: a navigation and working-context interface built on Lager's repository inventory and standalone worktree services.

The current intent is to bring helm.herdr's functionality into Lager through a clean rewrite. Preserve useful workflows, improve code structure, and seek measured responsiveness and modest visual improvements. Reassess the feature-level scope against actual usage and the host's capabilities when 2.0 work begins; this document does not freeze today's parity checklist.

Inventory remains the collection-management view. Forklift helps find and enter the right checkout, worktree, terminal context or agent. Their operations share application services rather than duplicating repository and worktree rules.

## Principles to retain

- **Independent helpers:** do not impose a start/resume/finish lifecycle.
- **Separate ownership:** Lager owns repository/worktree operations, Git owns its metadata, and the terminal host owns terminal sessions and focus.
- **Explicit actions:** closing a host workspace, removing a worktree and deleting a branch are different operations.
- **Exact destinations:** preserve concrete paths and host identities rather than guessing targets from labels.
- **Quality backed by evidence:** retain the intent for real terminal/host end-to-end tests and measured performance. Define detailed acceptance criteria when the feature scope is reviewed.

## Agreed host boundary

Forklift requires a supported terminal host. Herdr is the first planned integration; inventory and standalone repository/worktree commands remain host-independent. A host-free forklift mode is not required.

- Forklift owns general search, selection, browsing state and action requests.
- A small, typed host adapter owns discovery, interpretation of host topology and identities, and execution of host actions. Host commands and transport details do not leak into general interaction logic.
- Host-specific capabilities remain available without requiring every integration to reproduce them. Herdr's workspace → tab → pane hierarchy is not a universal model.
- A future integration should primarily add an adapter, mappings and tests, not rewrite Lager services. A substantially different host model may still need UI adaptation.
- Do not build a generic callback/plugin framework or implement a second host speculatively.

Nik identifies [Superlogical](https://www.superlogical.com/) as a possible future host and reports that its `rex` CLI will support scripting similarly to Herdr. Its topology and API are not established here. Shared subprocess infrastructure may help, but the boundary must translate host semantics, not just invoke a different executable.

## Interaction intent

For Herdr, retain the agreed requirement to initialize each workspace's selected tab from its active tab, rather than always starting at the first tab.

The HTML explores per-workspace browsing cursors, explicit focus activation, grouped related checkouts, layout requests and independent cleanup actions. Beyond the agreed active-tab initialization, these are ideas to revisit—not approved interaction or persistence rules.

## Revisit when 2.0 begins

- Which current helm.herdr workflows and preferences to carry forward, and any deliberate changes.
- Which management actions belong in forklift versus inventory.
- Host capabilities, topology, browsing/refresh behavior and unavailable-host diagnostics.
- Plugin installation, supported host versions, configuration/state transition and rollback.
- Concrete test journeys, performance targets and visual design.

These questions do not block 1.0. Let daily use of inventory and worktree commands inform the answers.
